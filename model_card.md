# Model Card — CVD Type & Severity Classifier

VisionAdapt's assessment flow uses this model to turn a user's color-plate
responses into a personalized correction profile (deficiency axis,
severity, and display type), replacing what was previously a fixed
if/else rule block.

## 1. What model is used

Two small feed-forward neural networks, trained with `scikit-learn`
(`MLPClassifier` / `MLPRegressor`, real backprop + Adam optimizer, not a
lookup table), then exported and run for inference in the browser with
**TensorFlow.js**.

| | Architecture | Task |
|---|---|---|
| Axis classifier | 12 → 16 → 16 → 3 (ReLU, softmax output) | Predicts confusion axis: Typical / Red-green / Blue-yellow |
| Severity regressor | 12 → 16 → 16 → 1 (ReLU, linear output) | Predicts deficiency severity, 0–100 |

Both run 100% client-side. No plate response, image, or profile data is
ever sent to a server.

## 2. Why a hybrid pipeline instead of one end-to-end classifier

An earlier version of this model tried to predict the full 7-class label
(Typical / Protanomaly / Protanopia / Deuteranomaly / Deuteranopia /
Tritanomaly / Tritanopia) directly. **Test accuracy was 47.5%** — not
because the model was undertrained, but because an 8-plate screening
battery genuinely doesn't carry enough signal to reliably tell protan
from deutan, or anomalous (partial) from dichromatic (complete)
deficiency, from binary right/wrong answers alone. Real ophthalmology
doesn't ask a screening plate set to do that either — that distinction
normally requires an anomaloscope.

So the pipeline was split to match what the input actually supports:

1. **Axis** (Typical / red-green / blue-yellow) — genuinely learnable
   from which plates get missed. Model-predicted, **83.8% accuracy**.
2. **Severity** (0–100) — genuinely learnable from *how many* same-axis
   plates get missed. Model-predicted, **MAE 16.7 points**.
3. **Fine-grained subtype** (protan vs. deutan; anomaly vs. opia) — not
   reliably recoverable from this input, so it's produced by an explicit,
   documented rule on top of the two model outputs plus the self-reported
   "which colors do you confuse" answer (anomaly vs. opia via a severity
   threshold; protan vs. deutan via self-report, since anecdotally
   protanopes describe reds as darker/brownish). This is a normal pattern
   in applied ML systems — model output feeding a decision layer — not a
   way of hiding rule-based logic; the rule layer is <15 lines and fully
   visible in `computeResultModel()` in `index.html`.

If we ever add plates specifically designed to separate protan/deutan
(vanishing-point-style plate pairs), that third piece could become
model-predicted too — see Limitations.

## 3. Dataset

**Synthetic, not real patient data.** VisionAdapt has no clinical trial
infrastructure or IRB, and real Ishihara-response datasets tied to
confirmed diagnoses aren't available for a use case like this — so rather
than skip ML or fabricate results on invented "real" data, training data
is generated by simulating plate responses using documented CVD
mechanics:

- Dichromats (`-opia`) fail same-axis plates near-certainly and pass
  orthogonal-axis / control plates.
- Anomalous trichromats (`-anomaly`) fail same-axis plates
  *probabilistically*, with failure rate increasing with severity — the
  actual clinical distinction between the two categories.
- Self-reported confusion is correlated with true axis but noisy, which
  is why a plate test is useful in the first place.

Full generation logic, with inline reasoning for every probability used,
is in [`../scripts/generate_dataset.py`](../scripts/generate_dataset.py).

- 6,000 training samples, 1,200 validation, 1,200 held-out test
- Classes balanced by design for stable training — **this is not a
  prevalence estimate.** Real-world prevalence is heavily skewed (e.g.
  deuteranomaly ~5% of males; tritan types <0.01%) and is not what this
  dataset represents.

## 4. Input / output format

**Input** — 12-dim feature vector, built fresh each assessment by
`buildCvdFeatureVector()` in `index.html`:

| Index | Meaning |
|---|---|
| 0–7 | One entry per plate (A–H) this session could show: `-1` not shown, `0` shown & wrong, `1` shown & correct |
| 8–11 | One-hot: which color pair the user self-reported confusing (Red/green, Blue/purple, Green/brown, Not sure) |

**Output:**
- `axisLabel` — one of `Typical color vision` / `Red-green deficiency` / `Blue-yellow deficiency`
- `axisProbs` — full softmax distribution (for the confidence shown in the UI)
- `severity` — float, 0–100

## 5. Inference pipeline

1. User completes the 5-plate + 2-preference assessment (unchanged UI).
2. `buildCvdFeatureVector()` assembles the 12-dim vector from the actual answers.
3. `CvdModel.predict()` runs both networks via TensorFlow.js tensor ops
   (`tf.matMul` / `tf.add` / `tf.relu` / `tf.softmax`), timed with
   `performance.now()` for a real, not simulated, latency figure.
4. `computeResultModel()` applies the documented subtype rule (§2) to
   produce the final type + severity shown to the user.
5. If TensorFlow.js fails to load or throws (e.g. blocked script, no
   WebGL/WASM), `computeResultFallback()` — the original rule-based
   logic, preserved unmodified — runs instead. **The UI always discloses
   which path ran** (a badge on the result screen and a stat in the
   Analytics → Model Insights panel), so a fallback is never presented as
   a model prediction.

## 6. Why this architecture

- **Small MLP, not a deep net or pretrained model**: the input is a
  12-dim tabular vector, not an image — there's no spatial or sequential
  structure for a CNN/RNN/transformer to exploit, and a large network on
  6,000 samples would just overfit. A small MLP is the appropriately
  sized tool.
- **TensorFlow.js over training a browser-native model**: training is a
  batch, offline, reproducible step (`train.py`) — there's no reason to
  pay training cost in-browser. TF.js is used for what it's actually
  good at here: fast, GPU/WASM-accelerated inference on a device with no
  Python runtime.
- **scikit-learn over hand-rolled backprop**: correctness of the
  optimizer (Adam, early stopping on a validation split) matters more
  here than framework novelty; sklearn's implementation is well-tested
  and the resulting weight matrices are trivially portable to any runtime.

## 8. Limitations — read this before trusting the output

- **Not a diagnostic device.** This is an accessibility/wellness feature
  for tuning game color correction, not a medical device, and is not
  validated against confirmed clinical diagnoses. It should never be
  described as diagnosing color vision deficiency.
- **Trained entirely on synthetic data.** The simulation encodes real CVD
  mechanics but has not been validated against real patient response
  distributions. Accuracy on real users may differ from the reported
  test-set numbers.
- **Protan/deutan and anomaly/opia are rule-derived, not model-predicted**
  (§2) — a genuine limitation of what an 8-plate screening set can
  support, not a shortcut taken to inflate scope.
- **Severity MAE of ~17 points is coarse.** Treat the severity score as a
  directional starting point for tuning correction strength, not a
  precise clinical measurement.
- **Class-balanced training data does not reflect real prevalence** — see
  §3. A model deployed against real-world traffic without this caveat
  could be misread as saying tritan deficiency is as common as
  deuteranomaly, which it is not.
- **No demographic or cross-population validation.** The synthetic
  generator does not model age, lighting conditions, or display
  calibration effects on plate perception.
